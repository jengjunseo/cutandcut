# 실제 파일 검증 기록

검증일: 2026-10-02. Windows, Google Chrome 154.0.8037.93, Node.js 24.12.0. 테스트는 설치된 Chrome의 네이티브 WebCodecs 디코더·인코더와 실제 파일을 사용한다. 다른 OS·브라우저에서 동일한 코덱 사용을 보장하는 기록은 아니다.

## 실행 결과

- TypeScript strict 검사와 Vite 프로덕션 빌드 통과.
- Vitest 편집 모델 테스트 14개 통과. 정수 타임베이스, 프레임 경계, 링크 분할·트리밍·잠금, 그룹 이동, 인접 클립 교환, 리플 구간 합집합, 잠긴 트랙·겹침 거절, undo/redo, 복사·붙여넣기, 전환 길이 제한, 프로젝트 검증을 포함한다.
- Chrome 통합 시나리오 5개 통과. 전체 실행 후 오디오 동기화 검사를 추가해 해당 시나리오를 다시 통과했고, 텍스트 드래그 Escape 취소도 별도 재검증했다. 총 소요 시간은 전체 시나리오 약 2분이며 실행 환경과 인코더 상태에 따라 달라진다.
- 배포 사이트에서 별도로 미디어 가져오기, 한글 합성, 미리보기 재생, MP4·WebM 네이티브 플레이어 재생, MP4·WebM·WAV·MP3 파일 다운로드 및 오디오 디코딩을 검사해 통과했다(57.9초). 배포 검증 원문은 [production.json](results/production.json)을 참조한다.

## 재현용 입력과 편집

`tests/fixtures.browser.ts`는 화면만 흉내 내는 데이터가 아니라 인코더와 muxer로 실제 파일을 생성한다. 첫 MP4는 빨강 영상과 440Hz AAC, 두 번째는 파랑 영상과 660Hz AAC다. 각 영상에는 움직이는 흰색 띠가 있다. 별도로 반쪽이 투명한 PNG와 220Hz PCM WAV를 만든다. 추가 시나리오는 JPEG, LAME MP3, VP8/Opus WebM을 실제 입력으로 사용한다.

기본 시나리오는 첫 영상 분할·0.8초 트리밍, 두 영상 순서 변경, 링크 오디오 동시 이동, 디졸브, 상위 PNG 및 두 줄 한글 텍스트, 음악 볼륨 41%·0.5초 페이드 인·1초 페이드 아웃, undo/redo를 적용한다. 프로젝트 JSON을 저장하고 같은 클립 배열을 복구한다. 원본 하나를 IndexedDB에서 제거한 뒤 같은 실제 파일을 다시 가져와 재연결한다.

## 출력 검사

| 결과 | 실제 컨테이너 / 코덱 | 픽셀 또는 샘플 크기 | 읽힌 길이 |
|---|---|---|---|
| 가로 영상 | MP4 / AVC + AAC | 1280×720 | 6.037333초 |
| 세로 영상 | MP4 / AVC + AAC | 720×1280 | 6.037333초 |
| 세로 WebM | WebM / VP9 + Opus | 720×1280 | 6.033초 |
| 오디오 | WAVE / PCM s16 | 48kHz, 스테레오 | 6.033333초 |
| 오디오 | MP3 / LAME | 48kHz, 스테레오, 192kbps | 6.072초 |
| 추가 입력 합성 | MP4 / AVC + AAC | 1920×1080 | 6.037333초 |

편집 스냅샷의 총 길이는 6.033333초다. 마지막 텍스트 클립이 첫 출력 프레임 뒤에서 시작한다. 영상 프레임 격자와 AAC·Opus·MP3 인코더 패딩 때문에 파일 컨테이너의 끝이 약간 다르다. 실제 파일을 다시 demux하고 디코딩해 해상도·코덱·길이·오디오 RMS를 확인한다. [상세 수치](results/editing.json), [1080p](results/compatibility.json).

0.5·1.5·2.25·2.6·3.2·5.8초의 디코딩된 출력과 공통 합성기를 비교했다. RGB 평균 절대 오차는 8-bit 범위에서 0.099~0.339였다. 손실 인코딩 차이를 포함한 값이다. 한글 줄바꿈·글꼴·위치, 투명 이미지, 레이어 순서와 컷 후 색상이 포함되며 원본과 결과 파일을 동일 프레임 시각에서 비교한다.

오디오 검사에는 100ms Hann 창의 주파수 진폭을 사용했다. 1.5·1.85초는 두 번째 영상의 660Hz가 약 0.12이고, 2.1·2.3·3.1·3.6초는 첫 영상의 440Hz가 약 0.12다. 4.4초 이후 원본 영상의 두 주파수는 사라지고 음악 220Hz만 남는다. 음악 진폭은 0.06147로 `0.15 × 0.41`과 일치했다. 5.7초 창에서는 0.01535이며 기준 진폭의 0.24966이다. [동기화·페이드 원문](results/audio-sync.json). 이 검증은 합성한 테스트 신호의 컷 전후 검사이며 모든 실제 촬영 파일의 동기화 보장은 아니다.

가변 PTS AVC 입력은 0·0.041·0.093·0.145·0.25·0.365·0.49·0.68·0.87·1.08초의 프레임으로 생성했다. 24fps 출력에서 0.1·0.25·0.5·0.8·1.2초를 읽고 프레임 시각 0.083333·0.25·0.5·0.791667·1.166667 및 예상 원본 색상을 확인했다. [VFR 수치](results/vfr.json).

## 오류·사용성 검증

- 깨진 AVI 입력 후 기존 자산·클립 유지, 원인/변환 안내.
- 출력 취소 후 Worker 종료와 편집 스냅샷 유지.
- IndexedDB 프로젝트 쓰기에 실제 `QuotaExceededError`를 주입해 저장 실패 표시와 편집 유지 확인. 성공으로 표시하지 않는다.
- 재로드 복구, 누락 파일 경고와 원본 재연결, 프로젝트 JSON 왕복.
- 한글 IME 조합 중 B 입력이 분할 도구를 작동시키지 않음.
- 390×844 모바일 레이아웃에서 미디어·속성 탭 조작. 모바일 OS 실기기 검증은 아니다.
- 키보드 도움말 Escape 닫기, 구분선 방향키 크기 조절, 조절 중 재생헤드 유지, Escape 텍스트 드래그 취소.
- 핵심 편집 시나리오의 브라우저 예외 0개, 원본을 포함하는 POST/PUT 업로드 0개.

## 성능 범위와 미검증 사항

프레임/PCM 전체 배열을 만드는 방식 대신 제한된 커서·Worker·작업 큐를 사용한다. 720p/1080p의 짧은 합성 파일 경로를 검증했다. 일반 중간 사양 PC의 장시간 편집, 4K, 수백 개 클립, 터치 실기기, Safari·Firefox·Edge, 임의 HEVC/AV1·MOV/MKV·FLAC/Ogg 파일 조합은 검증하지 않았다. 정확한 seek 지연·프레임률·메모리 장기 벤치마크도 아직 없으므로 무지연이나 모든 파일 지원을 주장하지 않는다.

현재 출력 제한은 5분, 예상 압축 파일 256MB, 최대 한 변 1920px다. 입력/출력 지원표와 남은 기능은 [README](../README.md)에 명시한다.

## 다시 실행

```sh
npm ci
npm run dev -- --port 5174 --strictPort
# 별도 터미널
npm test
npm run test:e2e
npm run build
```

배포 시나리오만 검사하려면 PowerShell에서 `$env:PRODUCTION_URL='https://cutandcut.vercel.app'` 설정 후 `npm run test:e2e -- --grep 'production bundle'`을 실행한다. localhost:5174 서버는 파일 생성·검증 도우미로 함께 필요하다. `artifacts/`에는 실제 출력 파일과 스크린샷이 생성된다. 저장소에는 개인정보 없는 작은 수치 기록만 `docs/results/`로 보관한다.

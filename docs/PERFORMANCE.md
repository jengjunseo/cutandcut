# 측정 기준과 번들 회귀 검사

2026-10-22 안정성 패스. 실행 환경은 Windows 10.0.26200, Chrome 155, Node 24.12, Ryzen 3 4100(논리 CPU 8개), RAM 약 16GiB다. WebCodecs의 실제 하드웨어 인코더 사용 여부는 관측하지 못했다. 실기기 모바일, 발열·장시간 부하, GPU/디코더 메모리 상한은 이 결과로 보장하지 않는다.

## 정적 빌드 기준선

`scripts/check-bundle.mjs`는 `dist/index.html`의 초기 JS와 정적 import를 추적한다. gzip level 6 기준이며 HTTP Brotli 전송량과 다르다. 시작 Worker는 별도 예산으로 검사한다. 인코더 WASM은 JS 안에 들어 있으므로 WASM을 별도 합산하지 않는다.

| 항목 | 변경 전 바이트 | 변경 후 바이트 | 허용 상한 |
| --- | ---: | ---: | ---: |
| 초기 JS gzip | 117,846 | 118,137 | 129,631 |
| 시작 Worker gzip | 213,552 | 214,281 | 234,908 |
| AAC/MP3 확장 JS 내장 WASM 합계 gzip | 388,388 | 388,385 | 427,227 |
| CSS gzip | 65,620 | 65,620 | 72,182 |
| 전체 폰트 배포 파일 raw | 9,724,900 | 9,724,900 | 10,697,390 |

초기 JS 증가량은 291바이트(약 0.25%), Worker는 729바이트(약 0.34%)다. 새 런타임 의존성은 없다. 전체 폰트 498개는 배포 파일 합계이며 첫 화면 다운로드 크기가 아니다. UI는 unicode-range에 맞는 조각만, Worker는 실제 텍스트에 필요한 조각만 로드한다. MP3 인코더는 약 311KB raw이고 시작 시 실제 출력 지원 확인에 사용된다. AAC 확장은 네이티브 AAC가 없는 경우에 로드한다. 이를 모두 초기 로드가 아닌 것으로 서술했던 첨부 문서의 가정은 수정했다.

```powershell
npm run build
npm run check:bundle
```

예산은 `scripts/bundle-budget.json`에 고정한다. 검사할 때 기준선을 다시 만들지 않는다. `--baseline`은 의도적인 재설정에만 사용한다. CI에서 npm ci → 단위 → strict/unused 타입 → 빌드 → 예산을 실행한다. 상한을 0으로 지정한 별도 테스트에서 exit 1, 정상 상한에서 exit 0을 확인했다.

## 초기 로드 측정

배포 빌드/HTTPS를 대상으로 새 브라우저 컨텍스트와 캐시 비활성 상태에서 측정한다. 첫 상호작용은 프로젝트 메뉴를 실제로 열고 확인한 시간이며 표준 TTI가 아니다. 출력 지원 검사 완료 시간은 별도 기록한다. 개발 서버의 모듈 다운로드량을 운영 성능 수치로 사용하지 않는다.

```powershell
npm run preview -- --port 5175 --strictPort
# 다른 터미널
$env:BENCH_URL='http://localhost:5175'
$env:BENCH_REPORT='artifacts/startup-performance.json'
npm run bench:startup
```

결과에는 JS/CSS/폰트/인코더 요청별 decoded 크기와 Playwright가 보고하는 encoded 크기를 분리한다. 일부 전용 Worker는 827KB 파일을 encoded 113바이트로 보고하므로 해당 wire 크기는 **미확인(null)**으로 남긴다. 나머지도 패킷 캡처 결과가 아닌 도구 보고값이다. 정적 gzip 예산을 실제 전송량으로 바꾸어 쓰지 않는다.

동시 검사가 없는 상태의 각 1회 관찰에서 기존 운영 버전은 메뉴 확인 557ms·출력 지원 확인 1,495ms, 최종 로컬 배포 빌드는 652ms·1,440ms였다. 서버·네트워크·압축 방식이 다르므로 이를 속도 개선율로 해석하지 않는다. 두 환경 모두 폰트 19개·182,652바이트 decoded, MP3 확장 311,247바이트 decoded를 요청했다. 전용 Worker는 미리보기와 지원 검사에서 각각 시작되며 요청별 decoded 합계에는 같은 스크립트가 중복될 수 있다. [관찰 수치와 범위](results/stability-startup.json).

최종 운영 배포의 별도 1회 관찰은 메뉴 550ms·출력 지원 확인 1,504ms였다. 변경 전 운영의 557ms·1,495ms와 큰 차이가 없으며 단회 수치로 개선율/회귀율을 판단하지 않는다. 폰트와 MP3 확장 decoded 요청 크기는 동일했다. Worker의 정확한 wire 크기와 실제 하드웨어 인코더 사용은 여전히 미확인이다.

## 영상 측정 하네스와 합성 기준선

`npm run bench:media`는 외부 파일을 명시했을 때만 해당 시나리오를 실행한다. A/B/C 실제 대상 파일이 없으면 건너뛰며 성능 결과를 생성하지 않는다. 사용자 영상은 브라우저 안에서만 읽고, 보고서에는 파일명·경로·프로젝트명·자막을 기록하지 않는다. 결과 JSON/출력은 커밋하지 않는 `artifacts/`에 남는다.

`npm run bench:fixtures`는 별도로 **저복잡도 합성 SDR 애니메이션+440Hz 소리**의 A/B/C 입력을 생성한다(로컬 개발 서버 5174 필요). 합성 데이터를 명시적으로 측정할 때는 `BENCH_SOURCE_KIND=synthetic`과 해당 파일 경로를 지정한다. 실제 촬영본이 없을 때 하네스가 이를 자동 대체하지 않는다. 여러 워커/검사가 겹치는 상태의 시간을 기준선으로 사용하지 않는다.

최종 배포 빌드(로컬 5175)에서 다른 검사/입력 생성이 끝난 뒤 각각 1회 실행했다. 입력은 모두 30FPS·SDR H.264/AAC의 저복잡도 이동 도형/색 전환/톤이다. 실제 촬영본·복잡한 컷·자막 다층 프로젝트의 기준선이 아니다.

| 시나리오 | 대상 | 가져오기/타임라인 | MP4 출력 | 실시간 대비 | 최신 탐색 응답 | 관측 메인 JS heap |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| A | 5분 1920×1080 → 1080p | 350ms | 75.5초 | 3.98배 | 132ms | 12.80MiB |
| B | 5분 1080×1920 → 세로 1080p | 229ms | 75.5초 | 3.97배 | 118ms | 19.54MiB |
| C | 1분 3840×2160 → 1080p | 336ms | 20.7초 | 2.90배 | 409ms | 10.02MiB |

실제 다운로드 크기는 A 12,114,414 / B 12,373,948 / C 2,407,952바이트다. 출력 FPS는 30, 길이는 각각 약 300.053 / 300.053 / 60.053초다. 네이티브 플레이어에서 10%·50%·90% 시각으로 탐색해 디코딩 가능한 readyState를 확인했다. 여섯 번 빠르게 요청한 탐색 중 최신 요청의 실제 Worker 프레임을 기다렸으며, 이 실행에서는 각 1개 응답 표본을 얻었다. 이를 평균/P95나 모든 요청의 응답으로 표시하지 않는다. 출력 완료 감지는 500ms 간격이므로 시간 수치에는 그 관찰 오차가 있다. [A](results/stability-benchmark-A.json) · [B](results/stability-benchmark-B.json) · [C](results/stability-benchmark-C.json).

측정 도구 첫 실행에서는 이전 프레임이 남아 있는 `aria-busy=false`를 최신 탐색 완료로 잘못 사용해 응답 표본 0개를 얻었다. 이 값은 결과로 채택하지 않았다. 실제 Worker seq의 최신 프레임 도착을 기다리도록 하네스만 수정해 세 시나리오가 통과했다(3.1분). 제품 코드를 바꾼 수정은 아니다.

```powershell
# 경로는 로컬 파일을 가리킨다. 파일을 서버에 보내지 않는다.
$env:BENCH_INPUT_A='D:\bench\landscape.mp4'
$env:BENCH_INPUT_B='D:\bench\portrait.mp4'
$env:BENCH_INPUT_C='D:\bench\4k.mp4'
npm run bench:media
```

가져오기부터 타임라인 표시/분석 종료, 빠른 6회 탐색 중 최신 프레임 응답, 실제 1080p MP4 출력 시간·실시간 대비 배속·다운로드 크기·네이티브 재생 metadata를 기록한다. 기본 원본 자동 보관도 포함한다. JS heap은 출력 중 500ms 간격으로 샘플링한 **메인 realm만**의 피크다. Worker, PCM, Blob/ArrayBuffer backing storage, 네이티브 디코더, GPU 메모리와 샘플 사이 피크는 포함하지 않는다. 이를 전체 메모리 사용량으로 해석하면 안 된다.

별도의 짧은 기능 회귀는 합성 SDR 4K60/회전 입력 2초를 실제 인코딩해 1080×1920·30FPS MP4로 출력·다운로드·디코딩한다. 이 검사는 방향·분할·재열기·프레임 격자·오디오가 유지되는지 확인하는 기능 검사다. 정지 색상표의 짧은 출력 시간을 위 1분/5분 측정이나 실제 촬영본의 속도로 대체하지 않는다. A/B/C 초기 합성 기준선을 확보했으며 실제 촬영본·실기기 모바일·큰 원본/많은 레이어의 성능은 미측정이다. 이 수치로 모든 영상이 3~4배속 출력된다고 주장하지 않는다.
